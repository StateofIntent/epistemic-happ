# A returning peer recovers far slower than a new one, because the unresponsive marker outlives the outage

**Repo:** holochain/kitsune2  **Component:** `kitsune2_gossip` / `kitsune2_core` / `kitsune2_api`
**Versions:** `kitsune2_gossip 0.5.0` and `0.5.2` (the relevant files are byte-identical between them), `kitsune2_core 0.5.2`, under `holochain 0.7.0`

## Summary

A peer that was known, went offline and came back recovers in **minutes**, while a peer that has never been seen gets the same history in **seconds**. Measured on two hosts across the public internet:

| case | result |
|---|---|
| brand-new node, same network seed, same moment | **all three claims on its first poll**, ~15s from not existing |
| the same node returning after a 861s outage | **nothing after 905s** |
| returning after 154s offline, nothing else joining | self-recovered in **304–309s** |
| returning after 884s offline, nothing else joining | self-recovered in **687–692s** |

The asymmetry is the finding: a stranger is cheap and an acquaintance is expensive, which is the opposite of what a user expects when they shut a laptop lid.

## The mechanism

Recovery is gated by a **URL-keyed "unresponsive" marker whose TTL is the peer's own `agent_info.expires_at`** — a value fixed *before* the outage began.

1. Any failed connection, failed send, or disconnect marks the peer unresponsive:

   > *"Call this whenever a connection to a peer fails to get established, sending a message to a peer fails or when we get a disconnected event from a peer."*
   > — `kitsune2_api-0.5.2/src/transport.rs:258-260`

2. The handler stores it keyed on the peer's URL, **with that peer's `agent_info.expires_at` as the marker's own expiry**:

   ```rust
   // kitsune2_core-0.5.2/src/factories/core_space.rs:310-314
   .set_unresponsive(
       agent_info.url.clone().unwrap(),
       agent_info.expires_at,
       when,
   )
   ```

3. Gossip target selection then skips any peer carrying it:

   ```rust
   // kitsune2_gossip/src/initiate.rs:269-275
   // Agent has been marked as unresponsive, we won't be able to gossip
   // with them.
   if peer_meta_store.get_unresponsive(url.clone()).await?.is_some() {
   ```

4. And the fetch queue drops that peer's ops from the request set — **with no log line at any level**:

   ```rust
   // kitsune2_core-0.5.2/src/factories/core_fetch.rs:346-352
   if peer_url_unresponsive {
       state.lock().expect("poisoned").requests
           .remove(&(op_id.clone(), peer_url.clone()));
   }
   ```

Agent infos live **20 minutes** (`core_space.rs:540`), re-signed once under 5 minutes remain, checked every 60s.

**So the controlling quantity is the residual lifetime of the peer's agent info at the moment contact was lost** — spread across roughly 300–1200s depending on where in its twenty-minute cycle the drop happened to fall. A new peer has no marker and no history, so it is never gated at all.

## Why this is worth reporting rather than tuning around

- The variable that decides recovery time is **not** the length of the outage, and is invisible to anybody operating the node.
- A round can complete and transfer nothing: gossip succeeds, op ids are enqueued, and the fetch queue silently discards them because the marker is still live. We saw 35 `NoDiff` messages carrying non-empty `new_ops` with the data never arriving, and the drop at `core_fetch.rs:346` logs nothing, so there is no way to see it happening.
- The marker is keyed on **URL**, so it is released by a URL turnover rather than by the peer demonstrably being reachable again. We observed exactly that: a node failing on one URL at t+25s and recovering on a new one **926.4s** later.

## What we are not claiming

We have not fitted a formula. The obvious one —
`recovery ≈ max(0, expires_at − t_reconnect) + one initiate tick` — fits a 154s outage (implying a residual of ~335s) and **fails** an 884s one, which would require ~1449s against a 1200s maximum. So a single marker with a single TTL is not the whole story; at minimum there are two independent markers (each side marks the other), re-marking on any post-reconnect failure can install a *fresh* 1200s expiry, and the fetch gate sits past the gossip gate.

We also want to correct something we previously believed and published: we attributed part of this to a 300s per-peer initiate floor. **That is wrong.** `min_initiate_interval_ms` (default `300_000`) appears only as a field, its default, a doc cross-reference and a test override — **no code in `kitsune2_gossip/src/` reads it**, in either 0.5.0 or 0.5.2, and its own doc carries a commented-out `#[deprecated]` saying it is being replaced by a burst mechanism. The live limiter is `AcceptBurstTracker::check_accept` (`respond/initiate.rs:176`).

## Suggested directions

Any of these would help, and we have no view on which is right:

1. **Release the marker on evidence of reachability**, not only on its TTL — a successful inbound message from that peer is proof the marker is stale.
2. **Key it on agent id rather than URL**, so a returning peer is not gated by a URL it no longer uses, and is not un-gated merely by changing one.
3. **Log the fetch drop** at `core_fetch.rs:346`. Nothing is emitted at any level when an op is removed for an unresponsive peer, so the gap between "ops were enqueued" and "ops never arrived" is invisible from the logs. This one seems worth doing regardless of the rest.

## Reproducing

Two hosts on separate networks, one DNA, no bootstrap in common with anything else. Write claims while one node is offline via `nmcli device disconnect` (not a conductor stop — that deletes the database and makes it a *new* node, which is the fast path and hides the bug). Bring it back and poll.

To see the mechanism rather than just the delay, capture on both sides: each side's view of the other's `agent_info` `created_at`/`expires_at` at disconnect **and** at reconnect, the peer URL either side of the reconnect, and `kitsune2_core::factories::core_fetch=debug`.
