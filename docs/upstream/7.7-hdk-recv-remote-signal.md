# HDK docs give a `recv_remote_signal` signature that cannot receive anything

**Repo:** holochain/holochain (`crates/hdk`)  **Component:** `hdk`  **Version:** `hdk 0.7.0`, `holochain 0.7.0`

## Summary

The doc comment on `send_remote_signal` tells you to write the receiving extern as:

```rust
#[hdk_extern]
fn recv_remote_signal(signal: ExternIO) -> ExternResult<()> {
    emit_signal(&signal)?;
    Ok(())
}
```

— `hdk-0.7.0/src/p2p.rs:138`.

Written that way, **every delivery fails to deserialize.** The receiving extern is never entered, and the sending side cannot observe the failure, so the symptom is that remote signals silently do not arrive.

The correct signature declares the payload's own type, not `ExternIO`.

## Why it fails

`send_remote_signal` msgpack-encodes the caller's payload and puts the bytes in `RemoteSignal.signal`:

```rust
// hdk-0.7.0/src/p2p.rs:152-157
h.borrow().send_remote_signal(RemoteSignal {
    signal: ExternIO::encode(input).map_err(|e| wasm_error!(e))?,
    agents,
})
```

The host then passes **those bytes as the extern input**, not an `ExternIO` wrapping them:

```rust
// holochain-0.7.0/src/core/ribosome/host_fn/send_remote_signal.rs:65
payload: signal.clone(),
```

So what arrives at `recv_remote_signal` is already the msgpack of the payload. `ExternIO` is

```rust
// holochain_integrity_types-0.7.0/src/zome_io.rs:19
pub struct ExternIO(#[serde(with = "serde_bytes")] pub Vec<u8>);
```

i.e. it deserializes from a msgpack **bin**. The arriving value is a msgpack **map** (or whatever the payload encodes to). `#[hdk_extern]` therefore tries to decode a map into a byte array and errors before the function body runs.

## Reproduction

Two conductors; a zome with an unrestricted cap grant on `recv_remote_signal`; send any struct or enum payload.

With `signal: ExternIO`, the receiving conductor logs a deserialize error whose bytes are the payload itself. Sending the enum variant `Saturated { domain, headroom }` produced:

```
Deserialize([129, 169, 83, 97, 116, 117, 114, 97, 116, 101, 100, ...])
```

which decodes as `0x81` fixmap with one pair, `0xA9` fixstr of nine bytes, `"Saturated"` — the payload, arriving where a byte array was expected.

Changing the signature to the real type fixes it with no other change:

```rust
#[hdk_extern]
pub fn recv_remote_signal(signal: MyPayloadType) -> ExternResult<()> {
    emit_signal(&signal)?;
    Ok(())
}
```

## Why this is worth fixing in the docs rather than leaving to discovery

The failure is unusually hard to attribute, because **neither side reports it in a form that points at the signature**:

- The **sender** cannot see failures at all. `send_remote_signal` is send-and-forget — the host's own comment is *"Timeouts and errors are ignored"* — so a sender observes a successful call and no delivery.
- The **receiver** does log a deserialize error, but it names the payload bytes rather than the mismatch, and at default log levels it is not visible.

The result is that a correct-looking implementation, written from the documented example, presents as broken propagation. In our case it cost roughly a day of looking at gossip, the cap grant, the peer store and the transport before the signature was suspected.

## Suggested fix

Update the example at `hdk-0.7.0/src/p2p.rs:131-142` to declare the payload type, e.g.:

```rust
#[hdk_extern]
fn recv_remote_signal(signal: MyPayload) -> ExternResult<()> {
    emit_signal(&signal)?;
    Ok(())
}
```

and note that the parameter type must match what the sender passed to `send_remote_signal`, because the host delivers the encoded payload directly as the extern input.

If `ExternIO` is the intended contract, then the host side is the bug instead and should wrap rather than pass through — but the docs and the implementation currently disagree either way.
